## 一、项目定位与基础并发

### 面试题 01：请介绍一下 CachePilot。为什么不直接使用 vLLM？

CachePilot 关注的是“哪些请求可以进入执行器、谁先执行、结束后资源是否回收”，
而不是“如何更快计算 attention”。它是 LLM Serving 的资源准入与调度控制平面，
负责请求生命周期、租户配额、逻辑 KV 预算、服务顺序及实验观测。

vLLM 更擅长底层模型执行、PagedAttention 和 continuous batching。项目已有
Sim、Torch 和 vLLM 执行器相关实现，但本轮 GPU 验证使用的是 Torch；不能把
Torch 实验说成 vLLM 的性能验收，也没有据此证明 SGLang 已完成集成。

两者不是替代关系：CachePilot 提供外层治理，vLLM 拥有内部 batch 和物理 KV。
我不会在 vLLM 外重复实现一套 GPU batch 调度器，否则容易产生双层排队和难以
解释的延迟。项目价值在于把资源控制策略及其正确性做成独立、可验证的模块。

### 面试题 02：这个项目有哪些亮点？哪一项有最直接的量化证据？

可以分为三个重点：Adaptive 准入提高逻辑预算利用率；WFQ 和 prefix-aware
调度接入真实执行槽；状态机、故障注入和证据归档形成验证闭环。其中量化证据
最直接的是 Adaptive，而不是缓存加速或高性能推理内核。

最新同轮实验中，Strict FCFS 拒绝率中位数是 29.6875%，Adaptive 为 0%，后者
三次均完成 64/64 请求。单请求逻辑 KV 峰值中位数从 131 降到 70 blocks，降低
约 46.6%。这是用历史输出估计减少保守预留带来的准入收益。

我会同时交代代价：窗口吞吐由约 35.79 降到 34.74 tok/s，Total P99 略有增加。
所以不能说全面加速，更不能说物理显存节省了 46.6%。能说明收益范围和实验
限制，比单独报一个很大的优化百分比更能体现对系统的理解。

### 面试题 03：一个请求从进入 Gateway 到完成，经历哪些阶段？

正常状态路径是：

```text
RECEIVED → TOKENIZED → QUEUED → ADMITTED → ROUTED → EXECUTING → FINISHED
```

入口先校验协议、租户和请求标识，再计算 prompt tokens 并注册请求。Admission
检查上下文、全局容量和租户配额；通过后预留逻辑资源，进入可调度状态。Scheduler
决定实际 dispatch 顺序，拿到执行槽后才进入 EXECUTING，执行器完成生成后更新
用量、学习历史并释放资源。

异常路径可进入 REJECTED、CANCELLED、TIMED_OUT 或 FAILED。状态机禁止非法
跳转和终态回退，例如不能从 FINISHED 再回到 EXECUTING，也不能在终态后继续
登记 token 输出。终态只能被一个竞争方成功提交。

还要区分状态名和实际排队能力：当前 Gateway 对准入容量不足通常直接拒绝，
不是所有请求都能无限等待；已准入但没有执行槽的请求才留在 Scheduler 等待。

### 面试题 04：Registry 如何实现幂等？同一个 key 提交不同内容会怎样？

Registry 把请求表和幂等索引放在同一把锁保护下，检查、创建请求、绑定幂等键
在一个临界区里完成，避免两个线程同时检查到“没有记录”后重复注册。

幂等键并不是全局字符串，而是带作用域的组合：

```text
tenant_id + API path + idempotency_key
```

同一作用域下还要比较请求 fingerprint。key 和 fingerprint 相同，Registry
识别为原请求；key 相同但内容不同，则返回冲突，不能悄悄把新内容套用到旧请求。
不同 tenant 的相同 key 不会相互去重。HTTP 层如何响应还取决于原请求状态，
不能把 Registry 去重直接等同于所有响应都能原样重放。

这保证的是单进程内注册和索引的一致性，不是分布式 exactly-once。扩展到多
进程时还需要共享存储、唯一约束或原子事务，否则每个进程都有自己的“唯一请求”。

### 面试题 05：为什么拆成多把锁？Python 有 GIL，还需要锁吗？

GIL 不保证“先检查、再更新”这一组业务操作原子化，也不替代共享状态的同步。
即使单次字典操作没有被打断，两次操作之间仍可能发生竞争；而且模型执行、
I/O 和异步任务本来就涉及不同执行上下文。

项目按数据所有权拆锁：Registry 锁保护请求表和幂等索引；每请求状态机锁保护
该请求的状态与事件；资源管理锁保护容量与租约；Gateway 另有调度状态的锁。
好处是不同请求不会因为无关的状态更新都争抢一把全局大锁。

拆锁也带来复杂度：跨组件更新不能自动视为一个事务，必须明确调用顺序、幂等
释放和失败回滚；同步锁内还应避免等待网络或模型执行。我的判断标准不是锁越多
越好，而是每份共享状态只有清楚的所有者，临界区足够小，竞争路径有专门回归。

## 二、资源预算与调度原理

### 面试题 06：逻辑 KV reservation 和物理 KV 有什么区别？容量如何估算？

逻辑 reservation 是控制平面承诺给请求的预算，用于判断还能否接纳新请求。
物理 KV 是执行器实际在 GPU 上持有的缓存，两者可能因预分配、碎片、对齐或
复用而不同，所以不能用逻辑 block 数直接宣称真实显存占用。

规划器先计算理论 KV 大小：

```text
每 token KV bytes = 2 × 层数 × KV head 数 × head_dim × dtype 字节数
请求 blocks = ceil((prompt_tokens + 预计输出 tokens) / block_size)
```

其中 2 代表 K/V；GQA 模型要使用 KV head 数，不能用 query/attention head 数。
容量换算还需要明确的 KV 专用预算，不能把 GPU 总显存全部拿来计算，因为权重、
激活和其他运行时开销也占空间。

当前 Torch 没有可靠的物理 KV handle 或逐请求占用信号，项目如实保留这个边界。
它能验证逻辑预算不越界，但不能仅靠这个公式保证实际执行永远不 OOM。

### 面试题 07：Strict Admission 和 Adaptive Admission 有什么区别？为什么用 P95？

Strict 按 `prompt_tokens + max_tokens` 预留，优点是保守、容易解释，缺点是
用户写了很大的上限但实际只生成几 token 时，逻辑预算被高估。Adaptive 保留
同样的硬限制，但把预计输出改成同 tenant、同 prompt 长度桶的历史统计值。

样本足够时，计算 `min(max_tokens, max(1, P95 + 安全余量))`；样本不足时回退
Strict。P95 使用 nearest-rank，历史窗口有上限，避免样本无限增长。请求成功
完成后，实际输出写回历史，同时记录首次估计的误差和低估次数。

选择 P95 是一个风险与利用率的折中：比均值更关注长输出，又不像历史最大值
那样容易长期保留过大的预算。但它不是未来请求的概率保证，更不是机器学习
模型。本轮估计为 45 tokens、实际输出为 1 或 37 tokens，因此减少了预留；
如果 workload 本来就频繁达到 max_tokens，收益会明显变小。

### 面试题 08：Adaptive 低估输出长度怎么办？能防止 GPU OOM 吗？

低估后不能直接无条件继续扩大预算。`reserve_generated_tokens` 根据累计输出
重新规划资源，先检查 max_new_tokens、全局 KV 容量和 tenant token 限额，全部
满足才增长 reservation；失败则返回 STOP_REQUIRED，由调用方终止并清理请求。

增长时不仅更新 Admission，还要同步 Registry 和 telemetry，否则会出现真实
控制账本与观测峰值不一致。完成时的估计误差始终相对最初估计计算，不能通过
中途扩容把低估记录“抹掉”。冷启动回退和安全余量只能降低风险，不能消除长尾。

我不会宣称这能防止当前 Torch 的所有 OOM。Torch 先完成整段 model.generate，
再向 Gateway 交付 token，因此 Gateway 的增长检查不是每个 GPU decode step
之前的物理分配门禁。要把保护前移到实际分配之前，需要执行器提供更细粒度的
协作接口；当前仍需要真实 CUDA 异常处理和恢复验证。

### 面试题 09：为什么同时限制 active sequences、token 预算和 KV blocks？

三个限制约束的不是同一种资源。active sequences 限制同时活跃的请求数量，
token 预算限制一轮执行的工作量，KV blocks 限制缓存预算。只限制并发数时，
同样 8 个请求可能是短问答，也可能是超长上下文，计算和存储压力差别很大。

在 Sim 的 RuntimeLoop 中，每轮先回收已结束请求，再准入新请求，然后按轮转
顺序分配 token 额度并推进执行。循环同时维护完整 reservation 和当前实际
逻辑 KV：前者为未来增长留空间，后者用于观察当前使用和验证峰值；仅看当前
使用量可能把容量都接满，导致已有长请求后续无法增长。

这里要明确实现范围：逐 tick 的 token 工作预算属于 Sim RuntimeLoop，不是
当前 Torch Gateway 的真实 continuous batching。Torch 侧主要通过准入配额
和单执行槽治理请求，不能把模拟器具备的 batch 控制能力直接算到 GPU 实现上。

### 面试题 10：WFQ 的原理是什么？怎样体现权重并避免饥饿？

WFQ 为请求计算虚拟完成标签，而不只是比较到达时间：

```text
virtual_start = max(类别虚拟时间, 同 tenant 上一次完成标签)
virtual_finish = virtual_start + service_cost / tenant_weight
```

同优先级类别中，选择各 tenant 队首里完成标签最小的请求。相同成本下权重越
高，标签增长越慢，因此获得更多服务机会。当前 Gateway 用 prompt+max_tokens
作为工作量代理，用 Fraction 避免浮点标签误差，同分时按稳定顺序打破平局。

正常情况下 interactive 优先；当某个 tenant 队首等待超过饥饿阈值时，WFQ
可跨类别按到达顺序提升它，防止低权重或 batch 请求一直被压制。

这不是对任意积压深度的硬延迟保证，也不能抢占已在执行的长请求。成本只是
token 代理量，和真实 GPU 时间有差异；本轮等权小样本也未证明 WFQ 显著优于
FCFS，要验证权重收益还需要不均衡租户负载和长期服务份额实验。

## 三、执行链路与故障恢复

### 面试题 11：为什么增加 execution_slots？有调度队列还不够吗？

如果 Gateway 将所有已准入请求直接送进 Torch，它们最终会在执行器内部的
generation lock 上等待。此时外层 Scheduler 虽然做过排序，却不再真正掌握
后续执行顺序，排队位置也难以观测。

项目把“占有逻辑预算”和“拿到实际执行机会”分开。本轮允许 8 个 active
reservation，但只发 1 个 execution slot，其他已准入请求留在 Scheduler。
只有调度选中并获得槽位的请求才进入 EXECUTING，结束后释放槽位，让下一请求
获得执行机会。选择顺序和 scheduler_wait_ms 都会留在请求诊断中。

单槽与当前 Torch 单请求执行语义一致，不是为了人为证明并发加速。增加槽数
也不会自动得到真正的 GPU batching；更换执行器时应按它的并发契约重新配置。
这次断连槽泄漏造成恢复请求超时，也说明槽本身必须作为资源参与清理和测试。

### 面试题 12：Prefix-aware 调度如何实现？为什么命中不等于加速？

项目用真实 token IDs 构建前缀索引，在同一作用域中找最长已记录前缀。作用域
包括 tenant、模型与 revision、tokenizer revision 和量化配置，避免把不同
租户或不同语义的 token 前缀视为同一缓存。Gateway 完成请求后记录 key，默认
有界保留 256 个唯一 key。

调度时用 `virtual_finish - hit_tokens / tenant_weight` 计算 cache 候选分数，
但不修改原始 WFQ 标签。只有候选真正越过基线请求才记 boost，并受连续 boost
次数、最大绕过等待时间和最低 tenant 服务份额限制，避免缓存偏好破坏公平性。

这只是逻辑命中和排序偏好。当前 Torch 没有物理 prefix KV 复用，不会因为
命中就少算 prefill；physical_hit 必须为 null。本轮三次 aware 的 boost 为
0/2/1，说明索引有效但提权覆盖不稳定，不能凭命中次数宣称性能提升。

### 面试题 13：取消、超时和完成同时发生，如何保证只有一个终态？

状态机把终态迁移放在每请求锁下执行，并用事件 ID 做幂等识别。多个竞争方
同时尝试结束请求时，只有第一个合法迁移能改变状态；之后不能再进入另一个
终态。重复事件不会重复执行，同一事件 ID 被用于不同操作也会被识别为冲突。

但“终态唯一”和“所有资源已释放”是两个问题。状态机主要保护状态，Registry、
Admission、Scheduler 和执行器各自还有副作用需要完成。资源租约有幂等释放
标记，Gateway 在最终清理中释放预算和槽位，执行器取消则按其机制协作停止。

因此测试不能只断言 state=CANCELLED，还要检查终态事件数、reservation、
active、执行槽和后续输出。取消后也不应继续交付 token。当前这些机制主要
保证进程内竞争的一致性，不承诺进程崩溃后副作用也具备分布式 exactly-once。

### 面试题 14：SSE 慢客户端会造成什么问题？项目怎样处理背压？

如果模型产生输出的速度一直高于网络发送速度，而服务把所有输出无限缓存，
慢客户端就会让内存持续增长，甚至影响其他请求。Gateway 的流式输出使用有界
asyncio.Queue，producer 放入队列时必须等待空位，从而限制这一层缓冲增长。

等待还受请求剩余 deadline 约束。客户端断连时通知执行器取消，清理 producer，
最后释放准入预算和执行槽。SimExecutor 也有有限输出缓冲，可以用逻辑时钟
稳定验证背压与排空，而不依赖真实网络的随机时序。

不过 Gateway 队列有界不代表整个推理过程内存都恒定：当前 Torch 先完成整段
生成，再交付 token，背压主要控制后续交付，不会让已经发生的模型生成倒退或
停止占用内部输出存储。要让 GPU decode 随客户端速率节流，需要真正逐 token
交互的执行器支持，不能仅凭 SSE 接口就声称实现了端到端流式背压。

### 面试题 15：讲一个项目中最有代表性的故障，你是怎样定位和修复的？

第二轮 Colab 中，断连请求已进入 CANCELLED，admission 的预留和 active 都
归零，CUDA allocated 也回到基线，但紧接着的恢复请求返回 504。这个现象说明
只看账本和显存不足以证明服务恢复，需要继续检查调度层是否还有资源被占用。

定位发现 SSE finally 先 await gather(producer)，然后才释放 execution slot。
Starlette/AnyIO 的断连 cancel scope 在清理 await 处继续触发取消，导致后面的
槽释放被跳过。单执行槽被残留请求占据，后续请求只能排队到 deadline。

先写 AnyIO cancel-scope 回归复现，再用 shielded scope 保护 producer 清理，
并通过外层 finally 保证账本和槽/事件释放。最新 GPU 结果中断连恢复已是
HTTP 200、FINISHED，槽和事件列表为空。经验是：异步 finally 里的 await
也可能被取消，恢复测试必须包含真正的新请求，而不是只断言资源计数为零。

## 四、实验方法与项目边界

### 面试题 16：为什么已经有 GPU 测试，还要实现 SimExecutor？

GPU 实验昂贵，而且结果受加载、CUDA 调度、网络和硬件状态影响，不适合承担
所有精细的状态竞争验证。SimExecutor 用固定 tick 和可控逻辑时钟模拟 prefill、
decode、KV 增长、batch 补位、输出背压及故障，让相同输入能够稳定重放。

实现中每个 tick 按固定顺序处理取消、缓冲排空、补位和执行；事件有递增序号，
不依赖墙上时间和全局随机状态。这样可以检查逐轮资源不变量，而不仅是最终
结果。例如发现某一轮 KV 越界时，可以定位到同一个 tick 和同一组请求。

模拟器用于验证策略与控制逻辑，不是 GPU 性能预测器。真实 tokenizer、CUDA
OOM、模型线程停止和 HTTP 断连等仍必须通过真实执行器测试。项目通过能力和
指标语义声明区分模拟结果与实测结果，不能把 Sim 的吞吐拿来宣传生产性能。

### 面试题 17：你怎样设计公平、可复现的策略对照实验？

先固定模型/tokenizer revision、硬件、执行器、软件快照、输入和 seed；每种
策略重启后 warm-up，再至少做三次正式测量。保存 manifest、trace、逐请求结果
和真实发送/完成时间，trace 哈希覆盖实际输入与 profile，而不只比较文件名字。

其次要验证策略确实触发。例如 Adaptive 必须存在非 fallback 和预留缩减，
prefix-aware 必须有命中及实际 boost，调度器必须经历可观测排队；否则性能
差异不能归因于相应策略。最后保留源码快照与 checksum，使结果能重新分析。

本轮是 closed-loop waves，每波结束才发下一波，不是固定到达时刻的开放环。
不同策略接纳的请求集合可能不同，所以吞吐和延迟包含准入效应，不能说成纯
调度消融。三次中位数只是描述统计，也不自动证明统计显著性。最新 400 个文件
校验、107 个源码 hash 和 25 份 summary 重算一致，支持证据完整性而非因果万能证明。

### 面试题 18：TTFT、TPOT、吞吐、公平性和成本指标有哪些容易误读的地方？

通常 TTFT 指首 token 延迟，TPOT 描述后续 token 的间隔，但解释必须结合执行器。
当前 Torch 整段 generate 后才向 Gateway 交付，因此这些是交付口径，不能当成
真实逐 token GPU decode 延迟；排队影响还应结合 scheduler_wait 和 total 分析。

窗口吞吐用实际观察窗口内输出 token 总数除以时长。拒绝率必须同时报告，否则
大量拒绝长请求可能让服务看起来更快。P99 对小样本很敏感，三次重复的中位数
也不是置信区间。公平性用 tenant 输出 token 的 Jain 指数，当前它不等同于
“按权重和需求归一化后的公平”，负载很均衡时接近 1 也不能证明 WFQ 的优势。

同样，逻辑 KV 峰值不是物理显存，GPU 秒和成本是估算，不是硬件计费实测。
本轮没有配置 GPU 小时价格，estimated_cost 为 null，因此不能给出真实省钱
比例。我的原则是先说明指标的测量语义，再谈优化幅度。

### 面试题 19：最新结果到底通过了吗？为什么日志 PASS，报告却没通过？

最新 `20260928T214914-3f3bc1` 中，渐进压测和五类 GPU 故障验证通过，但必要
对照为 INCONCLUSIVE，整体 Phase 1 是 NOT_PASSED。基础 phase1_exit 脚本的
PASS 没有包含 notebook 的完整策略覆盖条件，所以不能拿局部 PASS 替代最终结论。

阻断点是 prefix-aware 三次逻辑命中为 44/45/45，实际 boost 为 0/2/1，而门槛
要求每次都有真实提权。命中不意味着必须改序：两个租户都已预热，候选可能与
基线相同，也可能受公平保护约束。现有记录不足以逐次判断未 boost 的具体原因。

下一步应设计冷热候选同时排队的专门对照，记录基线/cache 候选、分数和保护
原因，并统一出口门禁，而不是删掉零 boost 的重复或放宽门槛让结果变绿。
故障方面已经五项恢复成功；OOM 是 model.forward 内真实 CUDA allocator 的
受控失败，不能写成自然负载下已经测出 A100 的物理容量上限。

### 面试题 20：如果要把项目推进生产或多 GPU，你会优先补什么？

我会先补证据与契约，再扩展规模。近期先让 prefix 对照稳定覆盖并统一出口，
随后在真实流式/batching 执行器上验证取消、指标语义和资源接口，避免把 Torch
单槽原型的结论直接搬到生产。观测不到的物理 KV 或命中继续保持未知。

多 worker 下，当前进程内锁和内存幂等表不再足够，需要请求所有权、共享幂等
记录、worker 心跳及失效后的租约回收。还要处理取消路由、旧 worker 恢复后的
过期写入，可以评估带版本的租约或 fencing token；这些是后续方案，不是现有
项目已经实现的能力。

生产入口还需要可信认证和 tenant 身份绑定，不能仅把请求头当作安全隔离；
同时完善有界排队、限流、过载降级和长期状态清理。性能验收则应增加开放环负载、
不同长度与租户权重、长时间稳定性和更多重复。优先级是可恢复、可解释、可验证，
而不是先增加 GPU 数量再处理一致性问题。

## 五、参数选择与性能权衡

### 面试题 21：Adaptive 的最少样本数、安全余量和历史窗口应该怎样选择？

三个参数对应不同风险：最少样本数控制什么时候开始信任历史，安全余量缓解
低估，窗口长度决定历史多久失效。当前 Gateway 配置至少 3 个样本、8 tokens
余量，Controller 默认每桶最多保留 1000 个最近样本。这是可运行的基线配置，
不是已经通过调参证明的最优值。

样本少时 P95 很不稳定，例如 3 个样本的 nearest-rank P95 实际就是最大值。
窗口大可以降低短期波动，但业务从短问答切换到长输出时适应较慢；窗口小响应
快，却容易被少量异常样本影响。安全余量大更保守，也会减少准入收益。

我会按不同窗口和余量做敏感性实验，同时观察低估率、增长拒绝、fallback、
完成率和延迟，不能只挑拒绝率最低的配置。若发现分布漂移，可考虑临时回退
Strict 或使用时间衰减，但这些是后续机制；当前按样本数量裁剪，不等于按时间
过期，也不能把统计估计当成未来输出长度的保证。

### 面试题 22：为什么按 tenant 和 prompt 长度分桶？这样会有什么盲区？

不同租户可能有不同使用习惯，长上下文和短上下文的输出分布也可能不同。
按 tenant 和 prompt 长度桶记录历史，比全局只维护一个 P95 更能区分负载，
同时让实现保持简单。当前 Gateway 的 prompt 桶边界为 128、512、2048 tokens，
长度更大的输入进入最后一桶。

盲区是“相同输入长度”不代表“相同输出任务”。一个请求要求只回答 OK，另一个
要求写长文，即使属于同一桶，输出也可能差很多。桶内混合分布会让短请求被
长样本拉高估计，或者新增长任务缺少相应历史；tenant 隔离也不是内容分类器。

细分任务类型可能改善估计，但会增加桶数和冷启动问题，不能只靠更细分就保证
更准。后续可以使用可信任务标签、模型版本作用域和样本量门槛，并与当前简单
基线比较。本轮模型固定，因此不能由本轮结果证明历史可跨模型、版本或量化
配置复用；这些变化应明确重建或隔离历史。

### 面试题 23：为什么接纳更多请求，吞吐却没有提升？该怎样选择并发上限？

准入决定多少请求可以进入系统，执行器决定单位时间能完成多少工作，两者并不
相同。本轮 Adaptive 减少逻辑预留，让 64 个请求全部完成，但 Torch 仍只有
一个实际执行槽。更多请求主要变成可见的排队，而不是 GPU 同时完成更多生成。

在稳定、同一统计口径下，可以用 Little 定律理解：平均系统内请求数等于完成
速率乘平均停留时间。如果服务速率基本不变而在途请求增多，平均等待通常上升。
但它是稳定状态的平均关系，不能拿小样本 P99 直接代入，也不能混用输入请求率
和只统计成功请求的完成率。

选并发上限时应扫描并发、长度和到达率，联合观察吞吐、排队、超时、拒绝率及
资源峰值，找到满足目标延迟的工作区间。当前 active=8、slot=1 是实验配置，
不是已经测出的通用最优值；只有执行器真正支持 batching 或并行工作时，提高
执行槽才可能产生计算侧收益，不能把放宽准入当成算力扩容。

### 面试题 24：项目会遇到队首阻塞吗？为什么不总是跳过放不下的大请求？

会。保持 tenant FIFO 时，大请求可能挡住同租户后面的短请求；在 Sim
RuntimeLoop 的准入重试中，被策略选中但 reservation 暂时放不下的请求还会
保留为 deferred 队首，下一轮优先重试。这是一种保持调度决定的取舍，而不是
始终追求每个时刻把资源填满。

如果随意跳过大请求，短期利用率可能更高，但持续到来的小请求可能让大请求
长期没有机会；同时会改变 FCFS/WFQ 原先承诺的顺序。优化时要明确是在提高
吞吐，还是在牺牲某些请求的等待和公平性，不能只看整体平均指标。

可评估有限次绕过、保留部分预算或更细的服务类别，并记录被绕过次数和长请求
尾延迟。但这些不是当前默认行为。还要区分执行路径：Torch Gateway 的容量
不足一般立即拒绝，它不是把 Sim 的 deferred 机制完整搬到 HTTP 队列中。

### 面试题 25：WFQ 为什么用 prompt+max_tokens 估计成本？这种估计准确吗？

它是一个易获得、可解释的正整数工作量代理：在执行前就知道输入长度和输出
上限，不必先运行模型才能排序。WFQ 用成本除以 tenant 权重计算虚拟标签，
因此即使成本不完美，也比完全忽略请求大小更便于分析策略行为。

但 prompt token 和 decode token 的单位成本不同，prefill 与 decode 也会受
输入长度、batch、硬件和执行器影响。max_tokens 又只是上限。本轮长 prompt
请求只输出 1 token、另一类输出 37 tokens，说明预算大小不等于实际服务时长；
当前成本模型不能被称为精确 GPU 时间预测。

后续可以用分阶段 profiling 建立 prefill/decode 的估计，或评估结合输出历史
的成本模型，并把预测误差纳入观测。但调整后也要验证公平性和长尾，避免低估
某类请求让它长期占便宜。Adaptive 预留和 WFQ 成本是两个独立决策，当前不能
假设 Admission 学到的 45 tokens 已自动用于 Scheduler 的 service_cost。

## 六、异步语义与接口可靠性

### 面试题 26：取消 asyncio Task，为什么不一定能停止 Torch 推理线程？

当前 Torch 通过 asyncio.to_thread 把同步生成移到线程中，避免阻塞事件循环。
取消等待这个结果的协程，主要取消的是异步等待关系，并不会安全地强杀已经
运行的 Python 线程或 GPU kernel。因此“HTTP 请求结束”不等于计算立即结束。

项目另有协作取消：按 request ID 设置取消标记，让 generation stopping
criteria 在模型生成过程中检查，并在后续交付处再次阻止 token 输出。这样
把取消意图传到执行器，但正在执行的单个计算步骤仍可能需要先返回检查点。

所以故障测试还要等待 generation lock 可取得、同步 CUDA，再核对分配与恢复，
不能只依据协程被取消就宣布物理资源回收。如果底层调用永久卡住，协作标记也
可能无法及时生效，生产中需要 worker 隔离、健康监测和有界重启策略。后者是
未来容错设计，当前不能声称已实现强制抢占或任意时刻的零延迟取消。

### 面试题 27：为什么 deadline 要用单调时钟？排队和执行能各重新计时吗？

超时衡量的是经过了多久，而不是日历时间。墙上时钟可能被 NTP 或人工调整，
如果直接相减，时间回拨可能让请求迟迟不过期，时间跳进则可能提前终止。
项目使用 monotonic 时间；测试可以注入逻辑时钟，稳定验证边界。

还要区分端到端预算和阶段预算。请求进入执行阶段后，可以开始新的执行阶段
计时，但不能抹掉客户已经在队列里消耗的总预算。有效截止时间应受端到端
deadline 限制，不能每次 await 或每生成一个 token 都重新获得完整超时时间。

Gateway 的等待使用剩余请求预算，独立的 RequestDeadlineManager 还提供排队/
执行阶段管理。它们不应被描述为完全相同的集成路径。多进程传递预算时也不能
默认不同机器的单调时钟数值可直接比较；需要传递剩余时长或定义跨主机时钟
协议，并考虑传输耗时。这一分布式协议尚不是本轮单机测试的验收内容。

### 面试题 28：为什么 SSE 请求 HTTP 200，最终仍可能失败？客户端该怎样判断？

SSE 响应头通常先发出，后续才持续发送事件。一旦响应头已经提交，就不能再把
这个 HTTP 200 改为 500 或 504。因此流式执行途中发生错误时，Gateway 需要在
事件流中发送错误信息并结束流；200 只能说明流式响应已建立，不代表生成成功。

客户端必须解析事件、识别错误与结束信号，并结合 request ID 查询最终状态。
同样不能把收到 [DONE] 就一概视为成功，因为错误路径也可能用结束标记收尾。
在响应尚未开始的校验、准入阶段，服务仍可通过普通 HTTP 错误表达失败。

验证时应分别覆盖“建立流之前失败”和“流中途失败”，检查终态、交付内容和
资源清理，而不是只统计状态码。客户端断连时已经无法可靠接收最后一个错误
事件，因此服务端状态和账本仍是必要证据；不能依赖向已断开的连接发送通知
来完成取消或回收逻辑。

### 面试题 29：遇到 429、504 或连接中断，客户端应该怎样重试？幂等能解决一切吗？

首先区分原因。429 可能是短期容量不足，也可能是上下文超限；后者不修改请求
就重试没有意义。504 或连接中断则存在“客户端没收到结果，但服务器已经执行
过一部分甚至完成”的不确定性，不能立即换新 ID 无限制重发。

如果请求有稳定的业务幂等键，重试应先保持同一 key 和内容，查询原请求状态，
遵守 API 的冲突和进行中语义。当前 Registry 能识别重复注册，但不等于 Gateway
已经实现完整的结果缓存与透明重放，也不保证失败请求会自动重新执行；明确
发起新尝试需要定义新的 attempt 及其与原业务请求的关系。

退避、随机抖动、最大重试次数和端到端总预算可以抑制重试风暴；是否建议重试
应依据机器可读错误原因，而非只看 HTTP 状态码。请求若关联外部副作用，幂等
还要覆盖那个系统，不能因为模型调用有 request ID 就宣称整条业务链 exactly-once。

### 面试题 30：healthz 和 readyz 有什么区别？为什么还需要故障恢复请求？

healthz 用来判断进程或服务入口是否活着，readyz 判断当前后端是否具备服务
条件。项目有这两个端点，readyz 会询问 backend.is_ready；模型还没准备好时，
不应因为 Web 进程能响应就把真实请求送进来。

但 readiness 也不自动覆盖所有内部状态。本项目曾出现模型和进程都还活着，
执行槽却泄漏的情况；一个简单 backend health check 未必能发现 Scheduler
永远无法发出新请求。这也是故障测试要额外提交真实恢复请求的原因。

生产中应区分低成本高频探针和低频端到端 canary：探针过重会自己占用 GPU，
探针过弱又发现不了控制链路失效。超时阈值、连续失败次数和恢复滞后需要设计，
避免暂时过载引发重启风暴。当前恢复验证说明本轮五类故障之后链路可继续工作，
不是对长期可用性或所有故障模式的保证。

## 七、对照设计与统计解释

### 面试题 31：warm-up 只是把模型跑热吗？为什么它会改变策略对照？

这里 warm-up 不只影响 CUDA 和模型初始化，还会更新 Adaptive 输出历史、
prefix 索引以及 Scheduler 的虚拟标签和服务记录。所以它同时影响计算状态
与控制平面状态，不能只说“排除了冷启动”而忽略策略已经学习了什么。

本轮每次重启后做串行同 workload 的 warm-up，再做正式测量。它能验证热历史
下的 Adaptive，却不能证明冷启动第一次请求也有同等收益。两个租户的两类
固定输入都预热后，正式请求普遍命中，也削弱了 prefix 冷热对照的区分度。

我会把预热内容和顺序当作实验协议保存，并分别定义冷启动、热稳态和分布变化
三个场景。若要清空某些策略状态，也应明确清空哪些、在所有对应策略下保持
一致并重新开始实验，而不是看到结果后再决定保留或重置。相同的预热请求序列
也不意味着不同算法最终内部状态完全相同，那本来就是策略差异的一部分。

### 面试题 32：怎样设计能稳定触发 prefix boost 的实验，而不是反复碰运气？

先明确测试目标：机制测试需要证明 cache-aware 在给定候选集合中改变选择，
性能测试则衡量自然到达条件下的整体效果。两者应该分开，不能为了出现 boost
改完时序后仍宣称是完全自然负载下的性能收益。

机制测试可预热指定 tenant/version 的长前缀，另一个候选保持相对冷；构造
满足“基线 WFQ 先选冷候选，但减去命中收益后热候选更优”的成本与虚拟标签，
并让两者在释放执行槽前都已进入队列。所谓冷也要核对实际 hit_tokens，因为
tokenizer 模板可能带来公共短前缀，不能只根据输入名字判断零命中。

同时确认没有触发等待或服务份额保护，记录候选、分数和保护原因，再用相同
条件跑 blind/aware 对照。生产式吞吐仍需独立重复实验。这个方案属于待补强的
验证设计；目前 GPU boost 为 0/2/1，不应删掉零值、增加随机重跑直到过关，或
把机制触发直接解释成物理 prefill 加速。

### 面试题 33：受控 CUDA OOM 和自然压测 OOM 有什么区别？看什么显存指标？

受控 OOM 是在指定位置故意申请明显超出容量的 CUDA 内存，验证异常识别、终态、
资源回收和后续恢复。本轮是在 model.forward 中触发真实 allocator 失败，
不是只手工抛一个带“OOM”字样的普通异常；但它不代表正常请求已经达到容量边界。

自然 OOM 来自真实长度、并发和执行器分配行为，需要逐级扫描并保留原始负载。
本轮渐进实验更多触及逻辑 KV 配额、active 和 context 保护，无法据此宣称已经
找到了 A100 40GB 的最大物理吞吐容量，更不能直接外推到更大模型。

显存还应区分 memory_allocated、memory_reserved 与设备级占用。PyTorch 可能
保留缓存池，reserved 不回到最低值不一定是活跃 tensor 泄漏；empty_cache
也不能释放仍被引用的 tensor。故障检查要结合同步、基线容差、执行线程停止
和恢复请求。当前已验证 allocated 回基线，不能把它改写成所有显存指标都归零。

### 面试题 34：开放环和闭环压测有什么区别？本项目为什么不能只看闭环结果？

闭环负载根据前一批完成情况继续发请求，系统越慢，后续到达通常也越慢。本轮
是 closed-loop waves，每波结束后才提交下一波，适合约束在途规模，并避免
拒绝后立即补发把实验变成拒绝风暴，但它会使到达过程受被测策略影响。

开放环按外部时间表或到达率发送，不等待上一请求结束，更接近“需求持续到来”
的过载情形。它能够暴露队列增长和延迟恶化，也更容易把服务压垮，需要明确
停止条件、最大积压以及超时预算，不能不受控地持续增加请求。

因此两种模型回答的问题不同。闭环中看起来稳定，不等于固定外部请求率下也
能满足 SLO；停止发送期间没有出现的请求还可能掩盖长时间拥塞，形成协调遗漏
风险。后续应补独立开放环实验，保存计划与实际到达时间、拒绝和超时，不能把
当前闭环数据重新标注成开放环，也不能混合两种吞吐口径得出一个优化百分比。

### 面试题 35：三次重复的中位数足以证明优化有效吗？应该怎样处理统计不确定性？

三次中位数适合作为初步描述，能够减少单次异常对展示值的影响，但不等于
统计显著，也不足以概括所有负载分布。尤其 WFQ/prefix 只有几个百分点的差异，
可能受到到达顺序、接纳集合、硬件状态和后台干扰影响，不能直接解释为因果收益。

比较时应先固定实验单位。不能把同一 run 内 64 个相互排队影响的请求都当作
64 次独立实验；更合理的是保留逐 run 结果，在足够重复后分析配对差值、离散
程度和置信区间。若做 bootstrap，也应考虑按 run 或相关簇抽样，而不是简单
打散全部请求。顺序交错或随机化能减少时间漂移偏差。

最重要的是预先确定主指标和成功标准，同时报告拒绝率与完成量。小样本 P99
尤其不稳定，不能看到哪个指标更好就换哪个作为主结论。当前 Adaptive 的准入
改善较一致，但吞吐没有提升；prefix 的覆盖本身尚不足，统计包装也不能替代
先证明策略实际参与了对照。

## 八、可观测性与工程演进

### 面试题 36：逐请求 telemetry 和日志会不会影响性能？怎样兼顾可追溯与隐私？

会。时间戳、锁、JSON 序列化、日志写入和大对象快照都消耗 CPU 与 I/O，尤其
在小模型或短请求场景可能占可见比例。应保证对照策略使用相同观测配置，并
单独量化开启观测前后的开销，不能默认监控是零成本的。

实验需要保留足够的逐请求证据，生产则可以区分低成本核心计数与详细诊断，
对后者考虑采样、有界异步队列和明确丢弃策略。指标 label 不应无界包含每个
request ID，否则时序数会膨胀；请求级细节适合放到受控日志或 trace 中。这些
生产优化是待评估方案，不是当前实验已经证明的吞吐能力。

隐私方面，正式 recorder 保存实际输入，本轮是合成 benchmark prompt，因此
便于重算；换成用户流量后不能照搬原样归档。需要脱敏、访问控制、保留期限与
删除策略。hash 有助于校验完整性，却不自动让敏感文本匿名，也不能替代对原始
prompt 和认证信息的保护。

### 面试题 37：Prefix 索引有上限，是否说明服务不会随运行时间增加内存？

不是。prefix key 默认最多保留 256 个，只约束这一类索引；请求注册表、幂等
记录、事件历史、telemetry、ledger、取消标记和输出结果还可能有各自生命周期。
一个容器有界不能推出整个进程有界，更不能从短跑峰值正常推出长时间无泄漏。

设计清理策略时要区分活跃状态和终态历史：活跃请求不能被 TTL 误删，终态记录
则可以在满足幂等、查询和审计期限后归档或清理。多个索引必须协调，不能只删
请求实体，却留下指向它的幂等键；也不能清得太早，让同一个重试被当作新请求。

后续需要持续多轮请求的 soak test，观察活跃数归零后的内存基线、各映射大小
和增长趋势，再结合对象引用定位。当前文档中的有界 prefix 与历史样本窗口
只是局部措施，项目尚不能凭这些机制宣称所有状态都已实现长期保留和回收治理。

### 面试题 38：如果新增一个执行器，怎样保证它不会破坏现有控制平面契约？

首先声明能力，而不是直接让它输出一组同名指标。要明确它是否流式返回增量、
batch 由谁管理、取消怎样生效、token 用量怎样统计，以及物理 KV 和 prefix
命中是否真的可观测。未知信号应保留 null，不能通过猜测私有对象补一个数。

其次做适配契约测试：重复或累计输出如何转换，取消后是否还交付 token，异常
怎样映射，request ID 是否原样传给 abort，完成时用量与终态是否一致。再用
Gateway 端到端测试验证预算、排队和清理，因为适配器自身成功不代表上层的
reservation 与实际执行生命周期已对齐。

最后再进入真实硬件验证和性能比较。vLLM 拥有 continuous batching，外层不能
按 Torch 单锁的假设控制所有内部步骤；跨执行器指标必须经过能力语义校验。
当前已有能力矩阵和适配实现，但本轮 GPU 是 Torch，不能把“接口能接入”和
“该执行器已完成生产规模性能验收”混为一谈。

### 面试题 39：为什么环境记录要包含 dtype、模型 revision 和源码快照？

相同模型名字不代表相同权重，分支或默认 revision 可能变化；tokenizer 版本
还会改变 prompt 长度和前缀匹配。dtype、GPU、驱动与依赖版本又会影响支持的
算子和执行性能。如果这些不同，观察到的差异不一定来自 Admission 或 Scheduler。

项目曾在 T4 上把包含模拟支持的 BF16 检测当成原生支持，后续改为检查
including_emulation=False。最新 A100 原生支持 BF16，所以本轮选择 BF16 合理，
却不能当作 T4 FP16 分支的复验，更不能把跨 GPU 的速度变化算成策略收益。

源码方面只记 commit 也不够：工作区可能有未提交修改，因此要保存执行时文件
hash 和快照；环境记录、模型/tokenizer revision 与原始结果一起归档。checksum
证明内容一致，不证明代码没有 bug。复现实验需要同时满足版本与协议条件，
而不是看到同一个仓库 URL 或同一个 notebook 名字就认为完全可比。

### 面试题 40：你会怎样组织测试，避免“覆盖率很高但线上仍出问题”？

我会按契约和风险分层，而不只追求行覆盖率。单元测试验证状态迁移、资源账本、
P95 分桶和调度顺序；集成测试验证 Gateway 到执行器的实际调用、学习反馈和
清理；真实 HTTP/GPU 故障测试覆盖进程、取消作用域、线程与 CUDA 的交互。

每个故障测试都应有完整断言：预期错误或终态、唯一结束、逻辑资源回收、执行
槽与事件清理，以及新请求可恢复。对曾出现的问题先写能在旧代码上失败的回归，
再修复并复验，避免一个测试实际上没有触发问题却一直绿色。SSE 断连案例就是
普通状态断言不足，而 AnyIO cancel-scope 回归补到了关键行为。

还要测试验证工具自身：缺失 manifest、错误指标语义、策略未触发或故障不足时，
门禁必须拒绝通过。skip 应说明缺失的覆盖，不能计为通过；本地无 CUDA 的结果
不代替 Colab GPU。长期运行、分布式恢复和生产认证等尚未充分验证的部分，应
明确列为待完成，而不是用现有测试总数替代能力边界。
